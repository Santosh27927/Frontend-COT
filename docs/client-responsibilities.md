# Client responsibilities in the browser prototype

The browser is the bridge between the player's input and the mock service. It does not decide whether a player can afford, unlock, earn, convert, build, cancel, or claim anything. The same boundary should remain when the Node mock is replaced with the real backend.

| Client responsibility                                                                 | Why the client handles it                                                                                                                                                                 | Server remains responsible for                                                                                                      |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Selected navigation tab, building, payment asset, converter pair, and quiz answer     | These are unfinished input choices, not account facts. The player can explore them without mutating a wallet.                                                                             | Allowed assets, options, lessons, building levels, and all validation                                                               |
| Rendering prices, balances, caps, production, reward results, and action availability | The browser must present the returned state and explain the available buttons. Values stay as decimal strings.                                                                            | Prices and valuation, exact quantities, capacity, costs, rewards, eligibility, and action acceptance                                |
| Requesting a quote after a click and rendering its returned lines                     | The user needs to review a concrete proposal before committing. There is no editable conversion amount.                                                                                   | Fixed source amount, rounding, bonus, binding quote expiry/ownership, available funds, destination room, and atomic execution       |
| Cancellation acknowledgement checkbox                                                 | Only this device can capture the user's explicit acknowledgement of the displayed loss.                                                                                                   | Original-asset refund calculation and validation of acknowledgement, construction identity, completion boundary, and refund credits |
| Native dialog focus, Escape, labels, keyboard and touch interactions                  | These are browser interaction concerns and need immediate feedback without network round trips.                                                                                           | The accepted command's effects; closing a preview never cancels an accepted action                                                  |
| Suppressing stale quote responses                                                     | A response for an abandoned selection or unmounted screen must not replace the current review. A request sequence and session generation guard this.                                      | Quote ownership, request validity, account revision, expiry, and confirmation                                                       |
| Owner-scoped stable intent recovery                                                   | A lost response does not establish whether the server committed. The client saves the original command before sending and retries that exact intent rather than generating a replacement. | Idempotency conflict checks, durable receipt and effects, rejection, and account/device authority                                   |
| Offline notice before a new action                                                    | The device can know it is offline before allocating an intent. It avoids creating an action the user might mistake for queued trading.                                                    | Final acceptance after reconnect; the client never treats its connection indicator as proof of success                              |
| Formatting returned timestamps in the player's local timezone                         | This is presentation only. The UI does not turn its local clock into financial or unlock authority.                                                                                       | Construction finish, lesson deadline, conversion cooldown, assistance timing, and quote expiry                                      |
| Lowercase account-name and four-digit PIN hints                                       | Immediate feedback reduces input errors and supports mobile keyboards.                                                                                                                    | Credential verification, the same validation, session replacement, and durable identity                                             |
| Responsive layout, readable light/dark colors, and CSS building illustrations         | Presentation must adapt to browser size. Artwork can be replaced by the design team without changing account rules.                                                                       | Building identity, catalog, reward and progression data                                                                             |

Business state is never written to browser storage. The existing session token/device identifier and a pending transport command are the only recovery data used by the UI. Developer clock/reset controls are visibly separated and hidden in production; they are not player rewards or gameplay buttons.

The optional knowledge checks render the correct answer on its own line and the explanation underneath. The server grades the selected answer, stores the accepted attempt count, and determines the one-time reward. The client does not maintain an answer key or reduce rewards itself.
